# 1.6G 内存的服务器，跑着四个容器

先交代一下硬件。

我的博客跑在阿里云最便宜的那一档云服务器上，2 核，1.6G 内存，Ubuntu 24.04。1.6G 是个什么概念呢，你电脑上开个 Chrome，多挂几个标签页，可能就不止这个数了。

就这么一台小破机器，现在跑着四个 Docker 容器，nginx 托管前台加反向代理，Go 编译出来的单二进制扛所有接口，MySQL 存数据，Redis 做缓存和在线统计，一天二十四小时转着。

这篇文章就讲讲它是怎么活下来的。

先说部署方式，因为它跟你在所有教程里看到的都不一样。

教程的剧本通常是，镜像推到仓库，服务器拉下来，完事。你可能会想，为啥不这么干呢，多顺啊。我也想。问题是我的服务器连不上 GHCR，连 Docker Hub 都超时，拉镜像这个动作在这个网络环境下永远走不通，试了好几次之后我认了。

既然搬不动仓库，那就自己当快递员。

本地构建镜像，docker save 导出来，gzip 压一遍，scp 扔上服务器，load 回去，compose up。全流程十五分钟上下，土，但每一步都在我掌控里。

说到这个，你可能觉得这管线也太原始了，CI/CD 一把梭不好吗。我理解，网络正常的话我也这么想。但在「连不上就是连不上」的现实面前，能跑通的手动管线，比跑不通的自动化先进一万倍。而且这个慢还带来一个意外的好处，因为发一次版有成本，我不再随手部署了，会把一批功能和修复攒成一个版本一起上，每个版本对应 git tag 和镜像 tag。发版从一个随手动作，变成了一个慎重决策，我个人觉得这是赚的。

然后是我认为整份 compose 里最值钱的一个细节，MySQL 的健康检查。

容器明明起来了，为啥还要专门拿 TCP 去戳它呢？

因为我的 MySQL 镜像首次启动时要导入初始化 SQL，这段时间容器看起来活着，但只有 socket 能连，TCP 层面根本不通。「容器已启动」和「真的能建立连接」，在那一刻是两回事。所以我的检查命令用的是 mysqladmin 的 TCP ping，配了三十次重试和三十秒的启动宽限。

后端的依赖也写了 service_healthy，等数据库真正可用才启动。不这么写的话，Go 服务会在 MySQL 还在导数据的时候就冲起来，连不上库，崩，重启，再崩，循环到数据库就绪为止。最后看似也跑起来了，日志里全是废掉的重启，万一哪次重试次数耗尽，就真的起不来了。

密钥这块只提一句，数据库密码和 JWT 密钥是首次部署时用脚本生成写进 .env.secrets 的，不进仓库，后端启动时还会拒绝空密码和示例密码。默认密码这种事，见得太多了。

日常运维就三件事，备份、自检、回滚。

备份，cron 每天 3 点 mysqldump 全量加打包图片目录，保留七天。自检，cron 每分钟跑一个探活脚本，查服务、内存、磁盘，结果写进 Redis，博客的状态页直接读它，等于这个网站每分钟自己摸一次脉。回滚，每次发版前，正在跑的镜像都会重打一个 rollback 标记留在服务器上，出问题不查问题，先把标记切回去，up 一下，一分钟回到昨天，然后再慢慢想哪儿错了。

配置是会骗人的。

有天晚上我给配置文件追加一段 AI 服务的配置，上传，重启，后端容器开始循环崩溃。我盯着日志翻了半天，缩进没问题，字段名也没问题。最后 diff 的时候才发现，原文件最后一行结尾没有换行符，我追加的内容直接焊在了上一行后面。

一个换行符。

它让配置文件里长出了 UseCdnDomains: falseAI: 这种鬼东西，YAML 解析当场去世。我对着这行字看了大概一分钟，说不出话。。。从那以后我改任何配置文件都会先确认文件末尾的换行，改完先在本地把服务起一次再上传。

比换行符更吓人的是备份。

有天我想把一份 mysqldump 的产物灌进一个「临时库」做恢复演练，操作完一看，正式库的表不对劲了。你敢信？？？查了半天才明白，dump 文件的头部自带 CREATE DATABASE 和 USE 语句，恢复进哪个库，从来不由你命令行里指定的库决定，由文件自己的 USE 说了算。我以为的「恢复到临时库」，实际是在往正式库里写。

这次演练还白捡一个认知，验证数据时客户端得带 utf8mb4，不然中文显示全是乱码，看着像坏了，其实用 HEX 一查字节好好的，差点手一抖重导一遍，把好数据冲了。

顺着事故这个话题再聊聊。后来我在一本讲航空安全的书里看到一个说法，民航业能把事故率降到今天这个水平，靠的从来不是不出事，而是每一次事故之后，都有一份不带责备的复盘。我的博客当然比不了飞机，但道理是通的，出事故不可怕，白交学费才可怕。备份的价值等于你演练过的那次恢复，没演练过的备份，只是一堆占硬盘的字节。

写到这里回个头。1.6G 内存，说出去都怕人笑话的配置，靠着 healthcheck、克制的发版节奏和一套土管线，稳稳跑了这么多天，一次没把我扔在半夜。

手动部署不丢人，网络不好就手动搬。丢人的是没有回滚方案，是备份从来没恢复过一次。

小机器有小机器的活法。
